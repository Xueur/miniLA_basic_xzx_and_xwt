# v8 最终修复：BRAM资源与访存握手

v8 保留 v7 的 BRAM 修复：把 160 KiB 地址空间显式拆成
`5 × 8192 × 32 bit`，Xilinx 7 系列映射为 40 个 RAMB36E1，低于
XC7A35T 的 50 个上限。

v8 另外修复了 v7 的流水线访存响应漏洞。原逻辑可能把前一笔
`daccess_rvalid/daccess_wresp` 当成后一条访存的响应，使后一条 `SW`
退休但没有真正写入 BRAM。CoreMark 中最先观测到的丢写是：

```text
SW 0x000001ed -> 0x0000d3f8
```

修复后只有在本条请求已经发出时才能接受响应，并且残留响应有效期间不会
发出下一笔访存请求。RTL 回归结果：

```text
MEM RESPONSE HAZARD TEST PASSED: no stale response reuse
crclist   = 0xe714
crcmatrix = 0x1fd7
crcstate  = 0x8e3a
FINISH
```

CoreMark 使用到的 `0x25800` 栈地址仍位于 Bank4 内，主存容量没有缩小。
默认活动测试已恢复为 `4_coremark`。

首次使用请把压缩包解压到新的英文短路径，不要覆盖 v6 或 v7，例如：

```text
D:\miniRV_CTEST_CoreMark_v8
```

进入 `miniRV_complete` 后双击：

```text
build_C_TEST_50MHz_bitstream_and_reports.bat
```

综合结束后应先看到类似：

```text
Post-synthesis BRAM usage: RAMB36E1=40, RAMB18E1=0
```

随后脚本才会继续 Implementation、时序检查和比特流生成。成功文件：

```text
output\miniRV_c_test_active_50MHz.bit
```

最终 WNS/WHS、功耗以及完整 CoreMark 跑分仍以本机 Vivado 2023.2 和
EGO1 开发板结果为准。
